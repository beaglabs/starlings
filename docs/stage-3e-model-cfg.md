# Stage 3E — Model-backed CFG validation

Stage 3E moves the context-free grammar candidate from deterministic protocol validation into model-backed A/B evaluation.

The experimental question is:

> For the same model, task, prompt, seed, and generation budget, does CFG-constrained decoding improve protocol validity and task success while reducing retries or communication overhead compared with typed but unconstrained generation?

## Architectural status

The CFG remains a **candidate architectural component**.

Stages 3C and 3D established deterministic evidence for:

- corpus coverage;
- malformed-sequence rejection;
- compositional parsing;
- exact round-tripping;
- generalization across unseen deterministic compositions;
- representation savings.

Stage 3E is the major remaining gate before architectural promotion.

Passing the Stage 3E harness tests does **not** validate the model-backed hypothesis. Actual model outputs must be collected and evaluated.

## A/B design

Each paired trial uses:

- the same model and model weights;
- the same quantization/runtime;
- the same workflow;
- the same prompt;
- the same experimental seed when the backend supports seeded decoding;
- the same generation budget;
- the same retry policy.

The only intended treatment difference is decoding mode:

### A — typed/unconstrained

The model is instructed to emit only protocol terminal names, but decoding is not grammar-constrained.

### B — CFG-constrained

The prompt is identical, but the backend receives the Stage 3C grammar as an out-of-band decoding constraint.

The evaluator exposes the grammar through `Request.grammar`; it does not append grammar text to the prompt. This avoids confounding prompt-token changes with constrained decoding.

## Workflows

Every model is tested against all six deterministic workflow families:

```text
OBSERVE   → CLAIM
QUERY     → EVIDENCE
PROPOSE   → ACCEPT
PROPOSE   → REJECT
CHALLENGE → RETRACT
DELEGATE  → QUERY → EVIDENCE → EVIDENCE
```

A structurally valid completion that solves the wrong workflow does **not** count as task success.

For example:

```text
QUERY EVIDENCE
```

is grammatically valid, but it fails an `observe_claim` trial.

## Metrics

Stage 3E records each decoding mode independently:

- total paired trials;
- generation attempts;
- first-try valid completions;
- eventually valid completions after retry;
- workflow task successes;
- grammar rejections;
- backend errors;
- generated bytes;
- completion tokens;
- latency.

Derived metrics include:

- first-try validity rate;
- eventual validity rate;
- task-success rate;
- average attempts;
- constrained-vs-unconstrained validity delta;
- constrained-vs-unconstrained task-success delta;
- retry/attempt delta.

The first two primary outcomes are **first-try protocol validity** and **workflow task success**.

Retries are measured because a system that only becomes valid after repeated regeneration may be substantially less efficient even if eventual success is equal.

## Model backend interface

The Zig core does not depend on a specific provider.

A backend implements:

```text
generate(context, Request) -> Sample
```

A request contains:

- workflow;
- seed;
- decode mode;
- attempt number;
- identical task prompt;
- optional CFG constraint.

A sample contains:

- parsed protocol terminals;
- generated byte count;
- completion token count;
- latency.

This boundary is intentionally compatible with:

- llama.cpp;
- vLLM;
- Ollama;
- local OpenAI-compatible servers;
- embedded inference;
- remote APIs;
- custom model runners.

Provider-specific transport belongs outside the mathematical core.

## Raw completion parser

`parseCompletion` converts terminal-only text into the typed protocol vocabulary without allocation.

Accepted example:

```text
DELEGATE QUERY EVIDENCE EVIDENCE
```

Rejected example:

```text
I think DELEGATE QUERY EVIDENCE EVIDENCE
```

This is deliberate. Extra prose is part of the unconstrained-format failure rate rather than silently being stripped away.

## Recorded live trials

Live model outputs can be captured and replayed through `RecordedBackend`.

The line interchange format is:

```text
workflow<TAB>seed<TAB>mode<TAB>attempt<TAB>completion_tokens<TAB>latency_us<TAB>completion
```

Example:

```text
query_evidence	42	cfg_constrained	0	2	1250	QUERY EVIDENCE
```

The raw completion is the final field.

This lets model transport remain separate from deterministic analysis:

```text
live model runner
      ↓
recorded trials
      ↓
Zig parser
      ↓
RecordedBackend
      ↓
same Stage 3E evaluator
```

## Recommended live experiment

For a first meaningful result:

- use at least 100 seeds;
- run all 6 workflows;
- test both decoding modes;
- use the same retry cap;
- record raw completions and metrics;
- repeat on at least two materially different model families if the goal is architectural promotion.

With 100 seeds, one model produces:

```text
100 seeds × 6 workflows × 2 modes = 1,200 paired-mode trials
```

before retries.

## Promotion criteria

The CFG should not become required architecture merely because constrained decoding guarantees syntactic validity.

Promotion should require evidence that constrained decoding provides a system-level advantage.

At minimum:

1. constrained decoding must not reduce workflow task success;
2. constrained decoding should materially improve first-try structural validity or reduce retries;
3. no workflow class should become systematically unreachable;
4. generated communication should remain at least as compact after accounting for constraint metadata;
5. the benefit should reproduce across seeds;
6. ideally, the benefit should reproduce across heterogeneous model families.

If constraints improve syntax but cause semantic/task degradation, the CFG should remain experimental or be revised.

## What the current PR validates

The Stage 3E implementation validates the **experimental machinery**:

- same-prompt A/B request construction;
- mode-specific grammar delivery;
- terminal-only completion parsing;
- structural validity measurement;
- task-success measurement independent of syntax;
- retry accounting;
- byte/token/latency accumulation;
- recorded-model replay.

It does **not** claim that a real model has yet passed the Stage 3E hypothesis.
